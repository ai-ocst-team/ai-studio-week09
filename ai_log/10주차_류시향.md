## 기록 01. 모듈 경계 Type Hint 뭉뚱그림(Any) 및 불투명한 Docstring 개선

- **품질 관점:** 가독성, 정적 안정성 (타입 명확화 및 모듈 간 인터페이스 투명성)
- **상태:** AI 생성 코드의 모호한 `dict[str, Any]` 반환 명세를 구체적인 `TypedDict` 및 필드 명세 Docstring으로 개선 완료

### 1. 초기 프롬프트

사용자가 AI에게 요청한 초기 프롬프트:

> Task 2 담당자로서 5개 모듈 함수(`prepare_photo`, `analyze_with_gemini`, `validate_vlm_response`, `clean_analysis_dataframe`, `aggregate_photo_insights`)의 파라미터 Type Hint와 반환 형식 docstring을 표준화하려고 해. `docs/schema.md`와 일치하도록 각 함수의 타입 힌트와 docstring 초안을 작성해줘.

### 2. AI 생성 코드

초기 AI가 제안한 모듈 함수 시그니처 및 Docstring 초안 발췌:

```python
from typing import Any, Dict

    Args:
        image_path (str): 이미지 파일 경로.
        
    Returns:
        dict: 이미지 데이터와 메타데이터가 담긴 딕셔너리.
    """
    ...

def analyze_with_gemini(photo: Dict[str, Any], model: str, hint: str) -> Dict[str, Any]:

    Returns:
        dict: VLM 평가 점수와 태그가 포함된 결과 딕셔너리.
    """
```

### 3. 사람이 발견한 문제·판단 근거

- **반환 구조의 불투명성 (`Dict[str, Any]` 남용):** AI가 반환 타입을 단순히 `Dict[str, Any]`로 뭉뚱그려 작성하여, 후속 모듈 담당자(Task 1 파이프라인, Task 4 테스트)가 실제로 어떤 키(`sha256`, `upload_bytes`, `safe_exif` 등)가 필수로 반환되는지 코드 내부를 열어보지 않고는 알 수 없었다.
- **docstring 명세 부실:** 반환 딕셔너리의 내부 제약 조건(예: 점수 범위 0.0~10.0, 6대 태그 카테고리별 최대 2개 허용, EXIF 화이트리스트 7종)에 대한 설명이 누락되어 데이터 계약 문서로서의 역할을 하지 못했다.
- **파이썬 최신 타입 문법 미반영:** `str | Path` 같은 최신 유니온 문법 대신 구버전 타이핑 문법이 혼용되어 있었다.

### 4. 수정·보완 내역

- 런타임 오버헤드 없이 정적 타입 검사(IDE/mypy)가 완벽히 지원되는 Python 표준 **`TypedDict`** 스키마(`PhotoPreparation`, `PhotoAnalysis`, `PhotoInsights`)를 `docs/schema_류시향.md`에 정의하고 이를 docstring에 명시하도록 수정하였다.
- 각 함수의 Docstring에 필수 반환 키, 값의 타입, 허용 범위 및 제약조건을 구체적인 표와 설명으로 보강하였다.
- `prepare_photo`의 입력 타입을 `str | Path`로 명확히 확장 정의하였다.

```python
# 수정 후 반영된 타입 명세 및 Docstring 표준
from typing import TypedDict, Any
from pathlib import Path

class PhotoPreparation(TypedDict):
    path: str
    sha256: str
    safe_exif: dict[str, Any]
    upload_bytes: bytes
    dhash: str
    width: int
    height: int

def prepare_photo(image_path: str | Path) -> PhotoPreparation:
    """사진 경로를 받아 VLM 업로드용 JPEG(최대 3072px)와 안전 메타데이터를 준비합니다.

    Args:
        image_path: 원본 이미지 파일 경로 (str 또는 Path).

    Returns:
        PhotoPreparation: 다음 필수 키를 포함하는 딕셔너리:
            - path (str): 정규화된 이미지 경로.
            - sha256 (str): 64자리 16진수 SHA-256 해시.
            - safe_exif (dict): 개인정보가 제거된 화이트리스트 7종 EXIF.
            - upload_bytes (bytes): 전송용 최적화 JPEG 바이트 스트림.
            - dhash (str): 16자리 Difference Hash.
            - width, height (int): 리사이즈된 이미지 치수.

    Raises:
        FileNotFoundError: 파일이 존재하지 않는 경우.
        ValueError: 지원하지 않는 이미지 형식이거나 파일이 손상된 경우.
    """
```

## 기록 02. EXIF 메타데이터 스키마의 개인정보(GPS/시리얼) 유출 취약점 차단

- **품질 관점:** 보안 (개인정보 보호, Privacy by Design)
- **상태:** AI가 제안한 포괄적 EXIF 스키마에서 위치정보(GPS) 누출 위험을 발견하고 화이트리스트 7종으로 엄격히 제한

### 1. 초기 프롬프트

사용자가 AI에게 요청한 초기 프롬프트:

> `docs/schema.md`에 들어갈 Step 1(prepare_photo)의 EXIF 메타데이터 스키마 명세를 작성해줘. 사진에서 추출할 수 있는 일반적인 카메라 촬영 정보들을 표로 정리해줘.

### 2. AI 생성 코드

초기 AI가 제안한 EXIF 메타데이터 스키마 표:

```markdown
### Step 1: 추출 메타데이터 스키마
| 필드명 | 타입 | 설명 |
|---|---|---|
| `camera_model` | str | 카메라 모델명 |
| `lens_model` | str | 렌즈 모델명 |
| `aperture` | float | 조리개 값 |
| `shutter_speed` | float | 셔터스피드 |
| `iso` | int | 감도 |
| `focal_length` | float | 초점거리 |
| `captured_at` | str | 촬영 일시 |
| `gps_latitude` | float | 촬영 위치 위도 |
| `gps_longitude` | float | 촬영 위치 경도 |
| `serial_number`| str | 기기 고유 일련번호 |
| `user_comment` | str | 사용자 코멘트 |
```

### 3. 사람이 발견한 문제·판단 근거

- **개인 식별 정보(PII) 및 위치 정보 유출 취약점:** AI가 일반적인 EXIF 항목이라며 위도/경도(`gps_latitude`, `gps_longitude`), 기기 고유 번호(`serial_number`), `user_comment`를 스키마에 포함시켰다.
- **보안 가이드 위반:** 사진 평가 파이프라인에서 GPS 좌표나 기기 일련번호는 사진의 미적 평가에 불필요할 뿐만 아니라, 향후 외부 VLM(Gemini 등)으로 전송될 경우 사용자의 사생활 및 위치 정보가 외부로 유출되는 중대한 프라이버시 침해를 유발한다.
- **실제 코드와의 불일치:** `prepare_photo.py`는 이미 안전한 화이트리스트 7개 태그만 조회하도록 구현되어 있으나, 스키마 문서가 이를 왜곡할 위험이 있었다.

### 4. 수정·보완 내역

- 위치 정보 및 식별자 메타데이터를 일체 배제하고, 사진 구도 및 촬영 조건 분석에 필수적인 **7종 안전 화이트리스트 EXIF**만 스키마에 허용하도록 엄격히 수정하였다.
- 허용 목록: `camera_model`, `lens_model`, `aperture`, `shutter_speed`, `iso`, `focal_length`, `captured_at`
- `docs/schema_류시향.md`의 보안 섹션에 "Privacy by Design" 원칙을 명시하여 GPS 및 개인정보 유출을 원천 차단하는 데이터 거버넌스 규칙을 확립하였다.

```markdown
# 수정 후 schema_류시향.md에 반영된 안전 EXIF 계약

| 필드명 | 허용 타입 | Null 허용 | 설명 및 보안 원칙 |
|---|---|---|---|
| `camera_model` | `str` | ⭕ 허용 | 카메라 기종명 (기본 IFD 0x0110) |
| `lens_model` | `str` | ⭕ 허용 | 렌즈 명칭 (서브 IFD 0xA434) |
| `aperture` | `float \| int` | ⭕ 허용 | 조리개 F값 |
| `shutter_speed` | `float \| int` | ⭕ 허용 | 셔터 속도 (초 단위) |
| `iso` | `int \| float` | ⭕ 허용 | ISO 감도 |
| `focal_length` | `float \| int` | ⭕ 허용 | 초점거리 (mm) |
| `captured_at` | `str` | ⭕ 허용 | 촬영 일시 (문자열 포맷 유지) |

※ GPS 좌표(위경도), 기기 일련번호, 사용자 메모 등 개인식별정보는 화이트리스트에서 원천 제외함.
```

### 5. 최종 검증 결과·Git 로그

- **검증 방식:** `prepare_photo.py`의 `BASE_TAGS` 및 `SUB_TAGS` 상수 매핑과 `docs/schema_류시향.md`의 일치 여부 확인, GPS 태그가 파이프라인으로 유입되지 않음을 검증
- **관련 커밋:**
  - 커밋 메시지: `feat(schema): restrict metadata contract to 7 safe exif whitelist fields for privacy protection`
- **적용 브랜치:** `feat/data-schema-contract`
