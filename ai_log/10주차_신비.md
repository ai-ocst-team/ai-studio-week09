## 기록 01. 통합 테스트에서 불필요한 Mock 의존성 검토

- **품질 관점:** 가독성, 불필요한 의존성 축소
- **상태:** 문제와 개선 방향 검토. 실제 이전 코드·커밋과의 대조 필요

### 1. 초기 프롬프트

사용자가 앞선 AI 대화에서 제시한 요청:

> pytest 만드려고 해.

이후 사용자가 생성 코드에 의문을 제기한 프롬프트:

> 근데 왜 너가 생성한 pytest는 안되는건데. 그리고 pipeline만 테스트하면 되는 거 아냐? 왜 analyze_with_gemini에서 모듈을 가져오는 거야?

※ 위 내용은 사용자 문서에 보존된 프롬프트이며, 최초 요청의 자세한 설명은 원문과 구분해야 한다.

### 2. AI 생성 코드

사용자가 보관한 기존 기록에 나타난 **초기 AI 제안의 핵심 구조**:

```python
from analyze_with_gemini import llm_client
from pipeline import run_pipeline

monkeypatch.setattr(
    llm_client,
    "generate_analysis",
    fake_generate_analysis,
)
```


### 3. 사람이 발견한 문제·판단 근거

- 통합 테스트의 목표는 개별 함수의 구현이 아니라 `run_pipeline()`의 최종 반환값과 예외 복원력을 확인하는 것이므로, 하위 VLM 응답 함수를 직접 대체하는 것이 반드시 필요한지 의문을 제기하였다.
- 제공된 `analyze_with_gemini.py`는 이미 `llm_client.generate_analysis()`를 사용하고, 제공된 `llm_client.py`는 고정된 Mock JSON을 반환한다. 이 구성에서는 테스트용 Mock 함수를 추가할 필요가 없다.
- `pipeline.py`의 `use_mock` 매개변수는 현재 함수 본문에서 모드를 전환하는 데 사용되지 않는다. 따라서 `use_mock=True`만으로 Mock 경로가 선택된다고 설명하면 부정확하다.

### 4. 수정·보완 내역

검토 후 선택한 테스트 구조:

```python
from pipeline import run_pipeline


def test_empty_folder(tmp_path):
    # 빈 폴더를 입력해 최종 반환값을 확인한다.
    result = run_pipeline(tmp_path, use_mock=True)
    assert result["total_photos"] == 0
    assert result["top_tags"] == []
```

- 테스트가 직접 호출하는 대상을 `run_pipeline()`으로 한정하고, 기존 Mock 클라이언트를 그대로 활용하도록 구성하였다.
- 팀원들의 `pipeline.py` 및 하위 모듈은 수정하지 않았다.

## 기록 02. `run_pipeline()` 통합 테스트 생성 및 반환 계약 보완

- **품질 관점:** 가독성, 검증 완전성
- **상태:** 초기 AI 생성 코드 및 보완안 확인. 실제 팀 저장소 적용·커밋 확인 필요

### 1. 초기 프롬프트

2026-11-09 사용자가 ChatGPT에 요청한 초기 프롬프트의 핵심 발췌:

> AI 오케스트레이션 팀 프로젝트의 **파이프라인 통합 테스트**를 담당하고 있어. 첨부한 실제 Python 파일을 바탕으로 과제를 완성할 수 있도록 도와줘.  
> `test/test_integration.py`를 작성하여 `run_pipeline()`의 전체 실행 흐름을 pytest로 검증해야 해.  
> Happy Path, 빈 폴더, 손상 이미지, EXIF 결측, 개별 이미지 실패 후 계속 처리를 검증하고 `tmp_path`를 사용해 줘. 불필요한 Mock이나 `monkeypatch` 없이 실제 모듈을 호출해 줘.


### 2. AI 생성 코드

AI가 처음 생성한 통합 테스트는 총 5개였다: Happy Path, 빈 폴더, 0바이트 이미지, EXIF 없는 이미지, 정상 이미지 사이의 손상 이미지.

초기 손상 이미지 테스트의 핵심 검증:

```python
result = run_pipeline(tmp_path, use_mock=True)
check_result_contract(result)
assert result["total_photos"] == 0
assert result["processed_count"] == 0
assert result["failed_count"] == 1
```

`check_result_contract()`는 반환 키의 **존재와 자료형**을 확인하지만, 빈 결과에서 `monthly_trend`, `top_tags`, `bottom_tags`가 정확히 비어 있는지는 검증하지 않았다.

### 3. 사람이 발견한 문제·판단 근거

1. **빈 데이터 계약 값 검증 누락:** 초기 손상 이미지 테스트는 반환 자료형을 확인했지만 `monthly_trend == {}`, `top_tags == []`, `bottom_tags == []`를 직접 검사하지 않았다. 일부 빈 결과가 잘못되더라도 통과할 수 있었다.
2. **EXIF 결측에 대한 Task 설명 오류 확인:** 실제 코드에서 EXIF 없는 정상 사진은 `safe_exif={}` → `captured_at=None`으로 처리되며, 날짜 결측만으로 사진을 제거하지 않는다. 이에 따라 정상 사진 1장은 `total_photos == 1`, `monthly_trend == {}`가 된다. **팀원 확인 결과, EXIF 결측 시 `total_photos == 0`이라고 쓴 Task 문구가 잘못된 것이고 1로 집계하는 것이 올바른 설계임을 확인했다.**
3. **Mock 사용 검토:** 제공된 `llm_client.py`가 이미 Mock 결과를 반환하므로 테스트용 `monkeypatch`를 추가하지 않는 편이 단순하고 재현 가능했다.

### 4. 수정·보완 내역

- AI가 생성한 통합 테스트에서 손상된 이미지의 빈 데이터 계약에 대한 구체적인 값 검증이 누락된 점을 확인하였다.
- `monthly_trend == {}`, `top_tags == []`, `bottom_tags == []` 검증을 추가하여 빈 데이터 계약의 검증 완전성을 높였다.
- 빈 폴더와 손상 이미지 테스트에서 반복되는 검증 조건을 `check_empty_contract()` 함수로 분리하였다. 기존 `check_result_contract()`를 재사용하여 중복 코드를 줄이고 가독성과 유지보수성을 개선하였다.
- EXIF가 없는 정상 이미지는 팀에서 확인된 설계에 따라 `total_photos == 1` 검증을 유지하였다.
- 팀원의 실제 구현 모듈은 수정하지 않고 통합 테스트 코드만 보완하였다.
