## R1 · 중 · Mock 해제 요청이 실제 호출 모드에 반영되지 않음

- 위치: 대상 파일 124~129행의 클라이언트 호출, `llm_client.py`의 `generate_analysis`, `pipeline.py:78`.
- 재현: 환경변수 `USE_MOCK=false`에서 분석 함수 정상 호출. 반환 final_score는 고정값 8.0이며 캡처한 stdout·stderr·루트 로그에 `[MOCK]`가 없다.
- 영향: 파이프라인은 use_mock 인자를 환경변수로 전달하지만 클라이언트가 읽지 않는다. 호출자가 Mock 해제를 요청해도 가상 결과를 실제 분석으로 오해할 수 있다. 실제 API 호출이나 개인정보 전송이 발생했다는 뜻은 아니다.
- 제안: Task 3에서 모드 선택을 연결하고 Mock 실행 표식을 출력한다. 실제 클라이언트가 미구현이면 비Mock 요청은 명시적으로 지원하지 않는다고 실패시킨다. Task 1과 전달 방식도 맞춘다.
- 검증 기준: Mock은 표식과 고정 결과, 비Mock은 실제 구현 또는 명시적 미지원 오류. 비Mock 요청을 조용히 Mock으로 처리하지 않음.
- 판단: 문제 확인, 구현 보류. Task 3 범위와 겹치므로 이번 자체 리뷰에서 변경하지 않음. 적용 커밋 없음.

## R2 · 중 · 통신 실패의 예외 계약이 파이프라인과 맞지 않음

- 위치: 대상 파일 130~131행, `pipeline.py:132`의 예외 처리.
- 재현: 정상 합성 사진 2장 중 첫 클라이언트 호출에 TimeoutError 주입. 분석 함수가 원인 연결된 RuntimeError("VLM 통신 실패")를 발생시킨다. 파이프라인 밖으로 전파되며 클라이언트 호출 횟수는 1회다. 두 번째 사진은 분석되지 않는다.
- 영향: 사진별 예상 가능한 통신 실패에서 전체 처리가 중단된다. 기존 통합 테스트는 손상 이미지 이후 계속 진행하는 경우를 다루지만 통신 실패는 다루지 않는다.
- 제안: Task 1·3에서 통신 실패의 계속 진행·중단 정책을 확정한다. 계속 진행 정책이면 도메인 예외를 정의하거나 알려진 통신 오류를 명확히 구분해 failed_count에 반영한다. 모든 RuntimeError를 무조건 무시하는 변경은 피한다.
- 검증 기준: 첫 사진 통신 실패 후 두 번째 정상 사진 처리 여부와 failed_count를 검증하는 통합 테스트 추가. 중단 정책을 선택하면 함수 계약·문서에 명시.
- 판단: 문제 확인, 정책·구현 보류. 현재 분석 함수의 오류 변환은 9주차 명세와 일치함. 적용 커밋 없음.
